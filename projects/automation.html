Scheduled Google Workspace automation

Internal tooling at DeviDevs: jobs that keep a spreadsheet honest, and a browser that fills in the gaps where there is no API to call.

Context
Internal tooling, DeviDevs, 2026
Stack
Python, Google Drive & Sheets API, OAuth, Playwright
Runs
Under launchd, unattended
Code
Internal — described, not published

This one is company tooling, so what follows is the shape of it rather than the source. No client names, no spreadsheet contents, no identifiers.

The problem

A shared spreadsheet acts as the record of which rows a person has taken. Several people work from it. When the process is manual, two failure modes show up immediately: someone works a row that was already claimed, or someone claims a row and forgets to write it down.

What I built

A Python module over the Drive and Sheets APIs with a deliberately small surface — status, find, and claim. The rule enforced in code rather than in a habit: rows are marked as claimed before any work starts on them, never after. It removes the window where two people can pick the same row, and it means an interrupted session leaves a correct record instead of an empty one.

It runs unattended through launchd — jobs on an interval rather than a terminal someone has to keep open — and requests are conditional, so an unchanged file costs a 304 instead of a download.

The browser half

Some tools have no usable API. For those there is a controller driving Chrome through the DevTools protocol with Playwright — a real browser session, doing what a person would do in the rich-text editors that reject synthetic input events.

I am wary of this layer and treat it accordingly. It breaks whenever the target's markup changes, so it is confined to the cases that genuinely have no API, and it is never the thing holding a credential.

The rules I work under

  • Read-only credentials where reading is enough. The Google credentials are scoped to read; sending mail directly through the API is switched off deliberately. Drafts get written, a human sends them.
  • Secrets live in one place and never anywhere else. Not in the repository, not in a log line, not in a report. Checking whether a secret exists answers configured or missing, never the value.
  • Anything published gets scrubbed. The sync feeding the front page of this site strips absolute paths, IP addresses, email addresses, and long hex strings out of commit messages before they are rendered — because a commit message written for me should not become a public one by accident.

Honest limits

  • A spreadsheet is not a database. The claim-before-work rule narrows the race, it does not eliminate it — the Sheets API offers no transaction across two people writing at the same instant. It is the right tool for this team's size and it would be the wrong one at ten times the volume.
  • Browser automation is a liability by nature. Every one of those flows is a thing that will break silently one day. They are worth it only where the alternative is a person doing the same clicks.
  • Little of this is covered by tests. Verification is running it and reading the result, which is honest but does not scale.

What I took from it

Almost all the value was in ordering, not in code: claim first, then work. The bug was never in the API calls — it was in the sequence people followed, and the fix was to make the wrong sequence impossible.
