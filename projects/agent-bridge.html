Answering a coding agent from my watch

The goal was a tap on the wrist and a one-word reply. The hard part turned out to be somewhere else entirely: two processes wanted to write to the same folder, and one of them was not me.

Context
Personal tooling, used daily at DeviDevs
Stack
Python 3, fcntl, launchd, Telegram Bot API (iOS + watchOS)
Status
In use, still changing
Code
Private — happy to walk through it

Why

I run coding agents on long tasks — refactors, audits, migrations. They work for twenty minutes and then stop to ask something, and until you answer, nothing happens. Being away from the desk meant losing the run.

The actual goal was narrower than "remote control": I wanted to answer from my wrist. Getting a tap on the watch, reading one line, and sending back "yes, continue" without taking the phone out is the difference between a twenty-minute pause and a five-second one.

Why Telegram, and not a web dashboard

A dashboard would have meant building and hosting a client, then building a second one for the watch, then dealing with push notifications on both. Telegram already ships a native app on iOS and watchOS, so notifications, replies and quick actions work on the wrist for free. Choosing the transport for the client it already has was the whole trick — the bot API is the boring part.

That decision moved the work to where it belonged: making the messages readable on a screen the size of a stamp. Agent output is verbose and full of paths, diffs and stack traces, none of which survive a watch notification. So the bridge summarises before it sends — one line of what happened, one line of what it needs, and the question phrased so the answer can be a single word. The full detail stays in the chat for when I am back at the laptop.

The part that was actually hard

Underneath sits a plain folder of Markdown notes that both the agent and I write to — notes, session logs, decisions, all versioned with git. Two writers, no database. The failure was immediate and ugly: the headless bot would commit at the same moment my interactive session did, and git would fail on index.lock. Worse than a crash, sometimes a note was half-written by one process while the other was reading it.

The fix is a single-writer lock around every write. Not a lock file that a process creates and deletes — that leaks the moment something is killed — but a kernel advisory lock: 

kw.sh with "<holder>" <command...>   # run command holding the lock
kw.sh commit -m "<message>"          # git commit under the lock
kw.sh status                          # who holds it, or "free"

Three properties made this worth doing properly:

  • The lock cannot leak. It is held on an open file descriptor, so the kernel releases it when the process exits — crash, kill -9, closed laptop, does not matter. No stale lock file to clean up by hand.
  • Waiting is bounded. A caller waits a configurable timeout (60 s by default) and can also ask for a non-blocking attempt, so a scheduled job that cannot get the lock gives up rather than piling up.
  • Readers are never blocked. Only writes serialise. Reading a note while something else is writing was never the problem worth solving.

One implementation detail I did not expect: macOS ships no flock command-line utility, so the shell wrapper delegates to a short Python script that uses fcntl.flock directly. The shell script is the interface; Python does the actual locking.

Scheduling

The bot and the bridge run as launchd agents rather than under a terminal I might close. Background jobs sync on an interval and notify on completion. Everything that writes goes through the same lock, including the jobs — that was the point.

Where it is rough

  • One lock for the whole vault. Coarse. Two writes touching unrelated folders still serialise. It is the right trade for a single-user system and it would not survive real concurrency.
  • The recovery story is git, not the daemon. If a write is interrupted between the file and the commit, I fix it by hand. There is no transaction spanning both.
  • It is tied to macOS. launchd and Keychain assumptions run through it. Porting to Linux means replacing the scheduling layer.
  • The messages are not end-to-end encrypted, and they should be. Traffic between the three endpoints — laptop, phone, watch — goes through Telegram's infrastructure in ordinary bot messages, which means the transport can read them. For what I send today that is a nuisance rather than a breach, but the content is repository names, file paths and occasionally a diff, and none of that belongs to a third party. Encrypting the payload before it is handed to the bot API, so Telegram carries ciphertext it cannot read, is the next thing on this project and is not built yet.

What I took from it

I had read about advisory locks in a course. Using one to fix a bug I actually caused taught me the thing the course did not: the value is not the lock, it is that the kernel releases it for you when your process dies. Every lock scheme I had written before that was a file I created and hoped to delete.
