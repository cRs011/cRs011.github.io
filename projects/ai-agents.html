Guardrails for AI coding agents

Everyone can get an agent to write code. The part that took me months was working out what to do when it writes something confident and wrong — which it does, and not rarely.

Context
Daily work at DeviDevs, 2026
Stack

Status

Code
Internal — described, not published

Most of my work now goes through AI coding agents. They are genuinely fast, and they are wrong in a specific way: fluently. A wrong function looks exactly like a right one. So the engineering moved somewhere I did not expect — away from writing every line, towards building the gates that catch the lines I did not write.

Three gates that run whether I remember them or not

A rule an agent is asked to follow is a suggestion. A rule the harness enforces is a rule. Everything below runs automatically, because the version that depended on me remembering did not survive contact with a long session.

What it may touch

Agents extend themselves by loading skill files, and a skill file is code. Anything installed goes to quarantine first, gets fingerprinted at approval, and is checked against that fingerprint before it runs again. An early version compared paths with a string prefix, which meant a directory called binEVIL passed as the authorised bin. That is not a hypothetical: I exploited it on my own system to confirm it, and it answered AUTHORIZED.

Read the whole file before changing it

The most expensive agent mistake I have seen is not a bad edit — it is an edit made after reading 40 lines of a 600-line file. A hook runs at the end of every turn and blocks completion if a file was modified after only a partial read. Cheap to enforce, and it removes a whole category of confidently broken changes.

Verify the claims, not the vibes

A script walks the documentation and checks every path it mentions against what is actually on disk — currently 536 references per run — plus a set of capabilities tested by executing them rather than asserting them. It exists because every real defect I found in that system was a false statement, not a bad structure.

There is also a red-team suite, 23 assertions, that tries to break the security boundaries on purpose. It went from finding real holes to passing, which is the only version of "secure" I trust.

Three times an agent was confidently wrong

A health check that could not fail

A vault health checker had been generated, reviewed, and used for weeks. It printed [PASS] on every line — as a literal, not as a result of comparing anything. The changelog proudly recorded a "90/90 PASS audit" produced by a script that was structurally incapable of reporting a failure. Nobody had read it closely because it always said what we hoped.

Statistics invented to be round

A summary of an exported chat archive claimed 1,744 conversations and 22,598 messages. Counted at the source: 1,553 and 18,910. A third figure was exactly double the truth, because every entry had been counted twice. The numbers were not random — they were plausible, which is worse. Now every figure in that system carries the command that reproduces it.

A delete that followed a symlink

A cleanup command with a trailing slash on a path followed a symlink into the real directory and removed a file that existed in no repository, because that folder was globally ignored. Recovered by rebuilding it from the sources that survived. The lesson was not "be careful" — it was that anything worth keeping has to be in version control before an agent is pointed anywhere near it.

What I would fix

  • The gates are Python scripts held together by config. They work on my machine and on the harnesses I use. Making them portable would mean a real interface rather than three files that know about each other.
  • A verifier that cries wolf gets ignored. The claim auditor reported a failure last week on the one sentence that said a file never existed — it matched the path and missed the negation. I widened the rule, but the general problem stands: a checker with false positives trains you to skip its output, which is worse than not having it.
  • None of this catches subtly wrong logic. It catches unread files, false claims, and broken boundaries. An agent writing an off-by-one in a scoring function walks straight through every gate I have. For that there is still only reading the code.

What I took from it

Working with agents made me a more suspicious engineer, not a lazier one. The habit that transferred to everything else: separate what I verified from what I assumed, and say which is which. Most of the bad calls I have made came from a sentence that sounded checked and was not — whether an agent wrote it or I did.
